# 卷日志的「抹除」——撤回（改 / 重发）之后旧内容仍在 `.ndjson` 里

> 立案：2026-09-19（会话树「枝」线收尾批 §5，用户裁定 P4-② 旧枝考古「不做」时点出：
> 「改 / 重发 这个东西其实就是破坏性的，甚至于你现在看历史都还在都算不正常，正常来说应该是旧消息直接抹掉的」）。
> 性质：**判定件**（只做判定 + 建议，**不写码**）——结论交用户裁。
> 状态：**已裁定（2026-09-19 用户「那就按A改」）→ A 案已落地**：设计裁定见
> `docs/plans/session-tree-plan.md` §12.9，落地记录见同件 §12.10。
> 关联：`docs/plans/session-tree-plan.md` §0/§6/§9（P4-② 不做裁定的落地后果指向本件）；
> `docs/plans/session-persistence-dsh-port-plan.md` §三「换轨后仍留的口子」第 2 条（同一口子，本件是它的判定）。

> **落地后的形状与本文档 §3 的一处偏差（留痕）**：动手时查实读路径
> （`loadSessionLogFile`）要求 **seq 连续**（`ev.seq !== 事件序号` 即判「序号断裂」停止认领），
> 故「保留原 seq、留空洞」必须**同时**给读路径一条「空洞可被声明」的规则；最终形状 = 头行
> `erased` 账为**唯一声明源** + 撤回事件退化为 `{0,0}`（no-op）+ **投影语义与事件词表零改动**。
> 三条实现裁定见 `session-tree-plan.md` §12.9（含「为什么压实只在接了落盘面时发生」——
> 它同时是「零 BCR」的证据）。

## 0. 一句话

**技术上按设计（append-only 事件日志 + 区间撤回事件，DSH 同族且更彻底），产品上不合约**：UI 把「改 / 重发」
呈现为破坏性操作，而旧内容**只从投影里消失、从不从卷文件里消失**（今天任何读面都看不见它，但它一直在、
还会被立枝复制放大）。用户已表态倾向「直接抹掉」——本件给出五种修法形状与代价，建议 **A（撤回即压实）**，
并明确：**选 A = 自觉偏离 DSH 同族语义**（§2.2），值得先落账再动手。

## 1. 现状（已复现，证据可重跑）

**机理（两处指针）**：

| 件 | 事实 |
|---|---|
| `src-ui/src/agent/session-log.ts:95` | `session/retract` 只记**区间** `{fromIndex, toIndex}`（不是内容，也不是删除指令） |
| 同文件 `project()` 的 `case 'session/retract'` | 投影里 `splice(from, to-from)`——**只影响读出来的消息表**，`_events` 与盘上文件一个字节不动 |
| `src-ui/src/app/chat/session-log-store.ts:285-315` | 落盘面**只追加**（`append_events`）；唯一的整份写（`write_log`）只在**首批物化**时发生一次 |
| `src-ui/src/agent/agent.ts:711-715` | `_retractSessionRange` = `append('session/retract')` + `session.splice(...)`——内存会话数组与事件日志**同时**前进，日志侧只多一条区间事件 |

**复现（临时探针，跑完即删；下面数字是它的输出）**：真卷 `[sys, 来文「原始问题」, 回复「原始回答」, 来文「第二问」, 回复「第二答」]`
→ 走真入口 `chat-session.retractUserMessage`（「改 / 重发」的撤回半边）→ 再续一轮「改写后的问题 / 改写后的回答」：

```
撤回前字节 686 → 撤回后字节 992        只增不减 ✓
旧内容仍在盘上（「原始问题」「原始回答」）✓      旧内容仍在投影里 ✗（投影已干净）
盘上 10 行：header / reset(init) / user / assistant / user / assistant / reset(adopt) / retract / user / assistant
```

⇒ **投影正确、日志留尸**：这不是「读出来是错的」，是「写进去的没被拿走」。

**代价面（诚实清点）**：

1. **卷文件只增不减**：每次「改 / 重发」都留下被撤回的原文 + 一条 retract 事件（两者都是永久增量）。
   **另有一个更大的增长源**（同一口子的另一半，本件一并登记）：`session/reset` 事件**携带整段消息表全文**
   （`agent.ts:699-700`）——每次恢复快照 / goal 清场 / 新建（`_replaceSession(..., 'restore' | 'new-session')`）
   都往文件里再写**一份完整历史**；`adopt` 是刻意做小了的那个例外（`agent.ts:736-737` 的注释明说：
   「整段替换要把全部消息再写一遍（每次开卷 +1 份全文）」）。
2. **立枝会放大它**：`createBranchVolume` 复制的是**父卷前缀的原始事件**（`session-branch.ts` 的
   `events.filter((e) => e.seq <= cut)`）⇒ 被撤回的旧内容**跟着复制进每一枝**
   （会话树计划 §8「磁盘成本」那条的实测形态）。
3. **「抹掉」的语义没兑现**：任何按**原始事件**重放的读面（未来的导出器 / 外部工具 / 直接看 `.ndjson` 的人）
   都会看到用户以为已经删掉的内容。
4. **不构成功能错误**（这点要说清楚）：今天所有**在册**的原始事件读面都**已经镜像了 retract 语义**——
   `danglingToolCalls`（`session-log-repair.ts:98-103`：遇 `session/retract` 清空悬空集）、
   投影 `project()`、立枝的落定校验都按「撤回后事实已变」处理。所以它是**存储与语义承诺**的问题，
   不是「读错」的问题。

## 2. 判性质

### 2.1 按设计，还是不合约？

**两者都是，要分开说**：

- **按设计**：phase-5 事件溯源立的就是「append-only 日志 = 卷本体」（`session-log.ts` 头注：双写期
  `this.session` 是真源 + SessionLog 逐字节等价）；区间撤回是**最小可重放**的撤回表达（记区间不记内容）。
  设计里**从来没有**承诺「物理抹除」——`session-persistence-dsh-port-plan.md` §三第 2 条把「无压实策略」
  如实登记为**已知口子**，会话树计划 §0 也把「历史还在」当**发现**写过。**DSH 同族（§2.2）走得更远**：
  它把被遮蔽内容建成可检索文档、人类转录刻意显示原文 ⇒ 「留痕」在同族里是**有意的产品语义**。
- **不合约**：产品面（「改 / 重发」这两个按钮）向用户承诺的是**破坏性**语义，而用户 2026-09-19 的裁定把
  这件事说死了：「正常来说应该是旧消息直接抹掉的」。⇒ **判定：不是实现缺陷，是产品语义的缺口（bug by contract）**——
  修它要动的不是某个函数，而是「撤回在盘上意味着什么」这条约定；而**改这条约定 = 偏离 DSH 同族**，
  必须显式落账（代价 = 丢掉「模型当时看见了什么」的取证能力）。

### 2.2 DSH 同族怎么做（外部仓 `D:\useful\deepseek-harness\`，2026-09-19 只读调研）

**结论：DSH 同样不物理删除，而且比兰台更「刻意」——它把旧内容当资产用。**

| 问 | DSH 的答案（证据指针） |
|---|---|
| 有 retract / rewind / truncate 吗？ | **没有**。日志层唯一的「破坏性」机制 = 在尾部追加一条携带 `surfaceOp: {op:'replace', startSeq, endSeq}` 的事件，**遮蔽**先前一段（`packages/core/session/src/types.ts:426-441`；折叠在 `surface.ts:519-522` 只改内存 surface）。持久化门面与 RPC 面**都没有**删除/截断方法。 |
| 旧内容还在文件里吗？ | **在，完整保留**（`session-persistence-jsonl` 的 `appendLines` 用 `open(path,'a')`）。真机实证：一个会话 12 处 replace，被遮蔽区间 7..491 的 **485 条原始事件逐条仍在同一文件**里。 |
| 有压实 / GC / 截断吗？ | **没有日志级压实**。`compaction/*` 是**遮蔽**（compaction-basic 的 `shadowedRange/shadowedSeqs` + `surfaceOp` replace），`session_projcache` 是派生缓存（从不改日志），唯一的 `truncate` 用于**崩溃撕裂尾部修复**。 |
| fork 动父卷吗？ | **不动**（`commands.ts:258-272` 拷 `seed` 前缀 + `parentSession`）——与兰台「枝即卷」同构。 |
| 只有投影看不到旧内容吗？ | **不是**，这正是关键：`session-query` 给每条原始事件打 `'current' \| 'shadowed' \| 'log-only'` 标签，**被遮蔽的照样建全文检索文档**（`documents.ts:36-73`）；**人类转录刻意显示替换前的原文**（`history.ts:393-395`），其注释写着：*"a landed replacement would erase conversation the user already saw"*。 |
| 有「改历史消息并重发」这个功能吗？ | **没有**（UI 的编辑只作用于尚未入日志的排队消息）——所以 DSH 从没遇到过兰台这个问题。 |

**这条调研改变了什么**：兰台的「日志留痕」不是实现漏掉的一步，而是**同族设计的默认语义**（DSH 把它做到更远：
遮蔽内容可检索、人类转录保留原文）。⇒ **「抹除」是一次自觉的偏离**，代价是丢掉「模型当时到底看见了什么」这份
取证能力（DSH 那条注释正是这个价值的表述）。这个取舍**只有用户能定**——所以本件不自行改语义（用户已表态倾向抹除，
但倾向 ≠ 已裁；偏离同族设计这件事必须显式落账）。

## 3. 修法形状与代价

| 形 | 做法 | 代价 / 风险 | BCR？ |
|---|---|---|---|
| **A 撤回即压实**（**已落地 2026-09-19**） | 撤回落定时**原子重写**该卷：把被撤回区间产生的**事件**与那条 `session/retract` 事件一并从文件里去掉（内存 `_events` 同步）。保留其余事件的 `seq` **原值**（留空洞、不重编号）⇒ 锚点不塌 | ① 撤回 = 一次整份重写（MB 级卷；走既有 `write_log` 原子替换，崩溃只留旧文件）；② **压实正确性判据必须是「重写后投影逐字节等价」**（fail-closed：不等价就不替换）——按 seq 数值区间蛮切会误伤（`adopt` 事件的锚点比尾部历史都大，见会话树计划 §12.5 的「锚点不假设单调」）；③ 要新开一条写路径（内存压实 + 盘上整写） | **否**（不新增 kind、投影与载荷字节零变化）——实测：`verify:convergence` 双轨零漂移（phase-5 T3 场景含 retract 但不接盘面 ⇒ 不压实 ⇒ 基线逐字节不变） |
| **B 关闭/退出时压实** | 同一机制，触发点换成「卷关闭 / 应用退出 / 空闲」 | 会话进行中仍有残留（用户看历史文件时还在）；实现面与 A 相同 ⇒ 先做 A 再谈要不要降频 | 否 |
| **C 只止放大**（半修） | 立枝复制前缀时**跳过**被撤回区间的事件（父卷自己的文件照旧留尸） | 最小改动（`session-branch.prepareBranchSeed` 一处），但「抹掉」仍未兑现——只解决 §1 代价 2 | 否 |
| **D 新事件 kind**（`session/erase` / 压实事件） | 用事件表达「抹除」 | 词表 + 投影语义变更 ⇒ **BCR 审批 + 双轨基线重录**；且它表达的还是「重写」，收益不抵代价 | **是**（不建议） |
| **E 不改**（日志当审计档） | 承认「撤回=投影语义，日志永久留痕」——**= DSH 同族的语义**（§2.2） | 与用户 2026-09-19 的表态直接冲突（「看历史都还在算不正常」）；立枝放大仍在 | — |

**为什么 A 不需要 BCR**：删掉的事件**本来就不进投影**（`project()` 对它们没有任何贡献），所以
「重写后的日志」与「重写前的日志」**投影相同、`derivePayload` 相同、前缀缓存字节相同**——这是 A 的
**验收判据**（不是它的假设）：压实前后 `deriveMessages()` / `derivePayload()` 逐字节对拍，差分矩阵补场景。
真正的风险不在语义面，在**实现面**（切哪一段事件、原子性、与写后队列的时序）——见 §5。

## 4. 我的建议（自裁部分，供翻案）

1. **做 A**（撤回即压实）。理由：用户已表态；A 不动词表、不动投影、不动载荷字节，是**唯一**能真正兑现
   「抹掉」而又不触碰前缀缓存的形状；C 只是止放大（可作 A 的副产品一并做）。
   **但这是一次自觉偏离**（§2.2：DSH 把留痕当语义，且它连「改历史消息」这个功能都没有）——
   落账一行「兰台在此偏离 DSH：撤回 = 物理抹除」即可，不必走 BCR（词表/投影未变）。
2. **触发点选「撤回落定即刻」**而不是关闭时：语义最直白（用户按下「改」= 那一刻就没了），
   且避免「会话还在跑、文件里躺着用户以为删掉的东西」这个最尴尬的窗口。
3. **验收判据（写死在测试里）**：① 撤回后 `.ndjson` 里**再也搜不到**旧内容（字节级 `includes` 断言）；
   ② 压实前后 `deriveMessages` / `derivePayload` 逐字节相同（差分矩阵）；③ 锚点仍单调可定位
   （`deriveMessageAnchors` 与重写前同长同序——枝线「从任意节点立枝」不受影响）；④ 原子性：
   写失败 = 文件保持原样 + 可见 warn（不静默、不留半个文件）。
4. **不做 D**（不值得为它走 BCR）。
5. **若用户要的是「保留取证但止增长」**：那是 E + C 的组合（承认留痕语义 + 立枝不再复制残留），
   本件同样成立——只是与「改 / 重发 = 破坏性」的措辞要对齐（按钮的承诺得改口）。

## 6. 复现方法（可重跑，不留码）

`{ws}/.lantai/sessions/{id}.ndjson` 的**字节数**与 `includes('旧内容')`；跑完即删（本件只留结论与数字）。
真机版：打开一卷 → 对某条来文按「改」→ 改几个字重发 → 用编辑器打开
`{工作区}/.lantai/sessions/{卷号}.ndjson`，搜旧句——**仍在**。
