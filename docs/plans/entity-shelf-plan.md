# 架阁（Entity Shelf）：软件的门 + 卡片的家

> **状态**：方案稿 v2（2026-12-08 立；同日按用户方向修订）。
> **方向已拍板（2026-12-08，用户原话）**：「放在 title bar 里面，点开之后打开一个专用的浮层窗，
> 这里面分开『软件型』和『卡片型』两页。」
> **一句话**：在顶部浮件加一枚**架阁**入口 → 打开一本**专用浮层窗**，两页分别陈列
> **软件**（点开窗）与**卡片**（点摊开）；卡片由此获得**实体身份与地盘**（能跨卷留住、能导出带走），
> 软件获得**一扇能点的门**（不必再靠 Agent 调工具开窗）。两者共用同一层「家」的底座。
>
> **来由**：用户 2026-12-08 问「软件类插件位的开放接口是不是比 showcard 先进，或只是过度设计？」
> 查证结论：**设计不超前，缺的是入口**（`docs/plugins/README.md` §9 未决项原话：
> 「软件级插件的管理 UI 面（启动器/任务栏）……待用户参与设计定稿后另批施工」）。
> 用户随后拍板两件一起做（选项 C），并选定入口形态（标题栏 → 专用浮层 → 两页）。
>
> **对照物**：`D:\useful\showcard`（外部开放规范）。本方案**不引入**它的标准使命与授权模型，
> 只采纳两条已验证的产品直觉（见 §3 D3/D4）。

---

## 0. 结论先说（给产品判断）

兰台今天同时存在两种「物」——**卡片**（Agent 现场造的资产块）和**软件**（装进来的插件应用），
它们各自缺一半：

| | 有什么 | 缺什么 | 缺的后果 |
|---|---|---|---|
| **软件** | 窗口原语 / 数据地盘 / 受治进程 / 后台唤醒（四件套齐全，跑得通） | **用户能看见并点开它的地方** | 只有 Agent 调 `notes_open` 才开得了——「一间只有 Agent 能进的房间」 |
| **卡片** | 流内渲染 / 画布摊开 / 本卷收纳条（图版架） | **离开本卷仍然存在** | 会话一删，卡片连同用户填的内容一起消失（状态按会话号落盘，明写不做跨会话共享） |

两件事表面无关，底下是同一个东西：**兰台的「物」都没有一个属于自己的家。**
软件的家的地基已经浇好（`~/.lantai/plugins-data/<插件名>/`），只差门；
卡片的家根本没建，身份还挂在会话号上。

**本方案的核心主张：一个入口，两个物种，一层底座。**——不新造第二套收纳面，
不给卡片单独造一套窗口系统，而是把两者收进同一本浮层窗，底座共用插件那套
已经验证过的「身份 + 地盘 + 生命周期」形状。

## 1. 现状实测（2026-12-08 查证，不是猜测）

### 1.1 入口位置（关键前提，用户说的「title bar」在兰台是什么）

- **画布视图没有传统标题栏**。2026-09-17「标题栏拆除批」把书眉布局行退役，
  画布铺满整窗（顶缘 = 屏缘），`--bar-h` 已删除、无任何消费面。今天承担标题栏职责的是
  **顶部浮件 `.pp-chrome`**（`PaperPanel.tsx:817`，带高 56 = 8 + 40 + 8），
  内容 = `画布` 二字（拖动抓手）+ 缩放读数 + 状态字 + 设置入口 + 回首页 + 窗口控制。
- **首页（SessionsHome）有顶栏 `.sh-head`**（约 88px）：印章 + wordmark · 右侧设置入口 + 窗口控制。
- → **本方案的「title bar 入口」落在画布顶部浮件**（主界面；首页后置，见 §3 D9）。

### 1.2 卡片侧

| 事实 | 证据 |
|---|---|
| 资产块 = `assetId → {kind, presentation, payload, ts}`；**payload 真源在会话 JSONL**，`asset-store.ts` 只是索引（可重建） | `src-ui/src/agent/asset-store.ts` 头注 |

| 图版架已落地：880×38 横条，收**本卷**全部 kind 资产，容量 6 +「… 另 N 张」，点 = 飞到流里、拖出 = 钉到纸上（随即离架） | `src-ui/src/plugins/builtin/compose-dock/AssetRack.tsx` |

| **删除通道从未建**：工具面只有 show / update / list，用户侧无删卡按钮（用户 2026-09 知情后暂缓） | 既有事实记录 |

→ **卡片的三个台阶今天只有前两个**：流里 → 纸上（`state='pinned'`）→ ~~架阁里（不存在）~~。

### 1.3 软件侧

| 事实 | 证据 |
|---|---|
| 窗口定义已在内存里成表：`defs[插件名] = {entryUrl, kind, mode, title}`，外加 `windows[]` 实例表 | `src-ui/src/state/plugin-window-store.ts` |
| 开/关/聚焦/查询已经是**宿主能力面**（`window.__lantai_plugin_host__.windows`） | `src-ui/src/plugins/window-facility.ts` |
| 数据地盘已落地：`~/.lantai/plugins-data/<插件名>/`，名字 + rel 双围栏，卸载整体挪 `.trash` | `src-tauri/src/commands/plugin_data.rs` |
| **管理 UI 未建**——原话：「窗口管理 UI 面（启动器/任务栏）形态待用户设计定稿后另批施工」 | `window-facility.ts` 头注 + `docs/plugins/README.md` §9 |

→ **四件套是资产，不是负债**；缺的是 `defs` 这张表**没人读给用户看**。

### 1.4 共同缺口

两者都缺「**上一级视角**」：今天所有东西都是**本卷**的视角——
图版架说「本卷还有什么没摆出来」，插件页说「装了什么」（藏在设置里）。
**没有一个地方回答「我手上有什么」**。这正是浮层窗要回答的问题。

## 2. 方案：一个入口，两个物种，一层底座

### 2.1 总览

```
   顶部浮件 .pp-chrome  ──〔架阁〕──▶  ┌── 架阁浮层（专用，两页）──────────┐
   （画布视图，56px 带）                │  〔软件型〕        〔卡片型〕      │
                                        │  · 笔记  ● 已开    · 本周待办     │
                                        │  · 天气  ○        · 读书清单     │
                                        │  点 = 开窗         点 = 摊到纸上   │
                                        └──────────┬──────────────┬───────┘
                                                   │              │
                                           ┌───────▼──────┐  ┌────▼─────────┐
                                           │ 软件（重）    │  │ 卡片（轻）     │
                                           │ iframe + 后端 │  │ 数据 + 渲染器  │
                                           └───────┬──────┘  └────┬─────────┘
                                                   └───────┬──────┘
                                                     ┌─────▼─────┐
                                                     │EntityHome │ 身份 / 地盘 / 生命周期
                                                     └───────────┘
```

**不新增家具、不动图版架**：架还是那件架（本卷收纳面，行为逐字不变）；
浮层窗是**另一件东西**——它回答的是「我手上有什么」，不是「本卷还摆着什么」。

### 2.2 底座：EntityHome（身份 / 地盘 / 生命周期）

三个能力，两种物各取所需：

| 能力 | 软件（已有，不动） | 卡片（本方案新建） |
|---|---|---|
| **身份** | `pluginName`（目录名即身份） | `cardId`（宿主分配，全局唯一，`card-<ts>-<rand>`） |
| **地盘** | `~/.lantai/plugins-data/<插件名>/` | `~/.lantai/cards/<cardId>/` |
| **生命周期** | 装载 / 卸载（`.trash` 回收） | 收起 / 删除（同款 `.trash` 回收） |

**为什么卡片放用户目录而不是工作区**：卡片是「我手上的东西」，不是「这个项目的文件」——
换工作区它也该在。栅栏（名字围栏 + canonicalize 前缀锁死）直接复用 `plugin_data.rs` 的写法。

### 2.3 面 A：卡片的家

**卡片包形态**（目录，不是单文件）：

```
~/.lantai/cards/<cardId>/
  card.json      # 身份与内容：kind / presentation / payload / title / source
  state.json     # 交互状态（html 卡的 window.lantai.state 落这里）
  assets/        # 可选：图片等资产（未来位，v1 不建）
```

**`source` 字段**（诚实记下来源）：

```jsonc
{
  "from": { "sessionId": "…", "assetId": "…", "projectPath": "…" },
  "shelvedAt": "2026-12-08T…",
  "stateAtShelve": 12345            // 收的时候状态多大（字节）
}
```

**三个台阶（关键，别和「钉到纸上」混）**：

| 台阶 | 动作 | 归属 | 会话删了会怎样 |
|---|---|---|---|
| 流里 | Agent `show_asset` | 本卷 | 没了 |
| 纸上 | 拖出钉住（已有） | 本卷（画布） | 没了 |
| **架阁** | **存进架阁**（新） | **宿主（跨卷）** | **还在** |

**「存进架阁」= 拓印，不是收藏链接**（借 showcard 的纪律，见 §3 D3）：
- 必须是**用户明确手势**（架阁里「收起这一张」），Agent 不得代收；
- 收的那一刻，把 payload 与**当刻状态**一起抄进 `~/.lantai/cards/<cardId>/`；
- 此后原件与副本**互不回写**——会话里那张改了，架阁里那份不动；反之亦然；
- 会话里那张卡被删 / 会话被删，**不影响**架阁里那份（本方案最核心的收益）。

**状态迁出的代价（诚实栏）**：`asset-state.ts` 今天按会话号落盘。新增卡片库后
**旧数据不迁移**（项目规范：旧格式读不进来就让它不存在）——`.lantai/asset-state/*.json`
留在盘上不动、代码不再读它；旧卷里的卡片状态等于清空一次。交付说明里要写明。

**删除通道一起建**（历史遗留的 D 面）：卡片库天然有「收起 / 删除」两个动作，
一次把资产块 CRUD 的 D 面补齐。

### 2.4 面 B：软件的门

**零新数据源**：`usePluginWindowStore.defs` 就是「已装软件清单」，今天已存在、
已随装载/卸载登记与注销。门只需要把它读出来。

**软件页的一条长这样**：

| 列 | 内容 | 来源 |
|---|---|---|
| 名 | `title`（manifest 的 `app.title`，缺省插件名） | `PluginWindowDef.title` |
| 形 | 浮动 / 停靠 / 全屏 | `PluginWindowDef.mode` |
| 态 | 已开（点 = 聚焦）/ 未开（点 = 开窗） | `windows[]` + `openWindow` |
| 身 | 出厂 / 第三方 / **提升来的**（provenance） | 插件清单 + `provenance`（若 dynamic-plugin-promotion-plan 落地） |

**不做的事**：浮层窗里不做「装/卸/禁用」——那是设置页的事。
门负责**开**，设置页负责**管**。一条边界，别把浮层窗做成第二个设置页。

### 2.5 入口与浮层（用户已拍板）

**入口**：顶部浮件 `.pp-chrome` 里加一枚**架阁**字件（两字，与 `画布` 对称；`--f-song`、
同号同墨，不自造字形）。**排在设置入口左侧**，与「回首页 / 窗口控制」同族。

**浮层**：专用浮层窗（`rootViews` 的 `'overlay'` 槽，与 ask / 权限提示卡同槽；
槽内无贡献 = 该层零渲染）。形态建议：

| 项 | 建议 | 理由 |
|---|---|---|
| 呈现 | 居中纸片浮层（宽 ~720、最高 ~70vh） | 与 `.pp-chrome` 同族判据：纸底 + 弱线 + 落影，**刻意不透明**（半透明会与底下正文糊字，`app/tip/tip.css` 头注已立此判据） |
| 关闭 | Esc / 点背板 / 右上角 × | 命令面板 `CommandPalette` 的既有交互同款 |
| 分页 | 顶部两枚页签：`软件型` / `卡片型` | 用户原话的两页 |
| 记忆 | 记住上次停留的页（会话内） | 小便宜，不必跨重启 |
| 空态 | 该页为空 → 一句诚实的话 + 指路（软件页：「还没有装软件——去设置 → 插件安装」；卡片页：「还没有存进架阁的卡片——在卡片上点『存进架阁』」） | 空态要有出口，不能只说「没有」 |

**为什么这个位置比架尾结好**（事后确认，写进决策）：
架尾结会污染「本卷还有什么没摆出来」这句诚实读数；浮层窗把**本卷**与**常驻**彻底分开——
架答「这卷」，阁答「我手上」。两个问题两个面，边界干净。

### 2.6 图版架：不动

本方案**不修改** `AssetRack.tsx` 的任何行为（≤6 张、点飞行、拖出钉、零张退场、
更新点、观察账一律原样）。唯一的接触点是 §5.3 里「在卡片上多一枚『存进架阁』的动作」——
落点是**流内卡片**（区块操作面）与**架阁内条目**，不是架。

## 3. 关键决策（自裁项，事后有异议再翻案）

| 编号 | 决策 | 理由 |
|---|---|---|
| **D1** | 入口 = 顶部浮件一枚字件；载体 = `'overlay'` 槽专用浮层窗；两页 | 用户 2026-12-08 拍板 |
| **D2** | 卡片数据落 **`~/.lantai/cards/`**（用户目录），不落工作区 | 卡片是「我手上的东西」不是「项目的文件」；换工作区该还在 |
| **D3** | 「存进架阁」= **拓印**，非收藏链接；**必须用户手势**；收后与原卡互不回写；**Agent 不得代收** | 借 showcard §3.2 的持久化梯度纪律：「收藏 ≠ 信任」 |
| **D4** | **不做**卡片的工具调用 / 网络授权（showcard 的三门系统） | 成本是一个安全子系统，当前收益为零；现有沙箱（`connect-src 'none'`、无 same-origin）是资产不是缺陷 |
| **D5** | **不做**跨软件标准 / `.card.zip` 交换格式 | 生态为零；真要「带得走」，导出单文件 HTML 比需要对方装宿主强一档（§6，可后置） |
| **D6** | 卡片状态**旧数据不迁移**（`.lantai/asset-state/` 归档不读） | 项目规范：旧格式读不进来就让它不存在。迁移是双读化石的起点 |
| **D7** | 卡片库写盘走 **Rust 命令**，不走前端拼装 | 前端无盘权；与 `plugin_data.rs` 同族（写盘必须在壳侧） |
| **D8** | 浮层窗**只管开**，装/卸/禁用仍归设置页 | 一门一职；混职责会让它变成第二个设置页 |
| **D9** | **首页顶栏（`.sh-head`）本批不放**入口 | 首页是案卷列表，「我手上有什么」主要在工作态用；且首页顶栏右侧已排设置 + 窗口控制。真需要时同一枚字件搬过去即可（同一组件、零返工） |
| **D10** | 浮层窗**不做拖动/缩放**（固定居中） | 它是一次性查询面，不是常驻窗；拖动会让人误以为可以一直在那儿 |

## 4. 数据形状

### 4.1 卡片记录（`card.json`）

```jsonc
{
  "cardId": "card-1733654321-a8f3",
  "kind": "html",                     // 复用既有 11 kind，不新增
  "presentation": "html",
  "title": "本周待办",                 // 缺省 = kind 名（不编造）
  "payload": { "code": "<div>…</div>" },
  "source": {
    "sessionId": "…",
    "assetId": "…",
    "projectPath": "…",
    "shelvedAt": "2026-12-08T10:11:12.000Z"
  },
  "v": 1                               // 卡片库格式版本（不为兼容留旧分支，只为将来迁移/拒绝）
}
```

### 4.2 卡片状态（`state.json`）

沿用 `asset-state.ts` 的语义**逐字不变**：浅合并 patch、值必须 JSON 可序列化（深校验 + 环检测）、
**64 KiB 上限**（合并后序列化字节数、超限整笔拒绝、绝不半写）。只换存储位置与键——
从 `(sessionId, assetId)` 换成 `cardId`。

### 4.3 RPC（snake_case，全部新增）

| 方法 | 参数 | 返回 | 性质 |
|---|---|---|---|
| `card_shelve` | `{ card_json, state_json }` | `{ cardId, dir }` | 写盘（拓印） |
| `card_list` | `{}` | `{ cards: [{cardId, kind, title, shelvedAt, bytes}] }` | 只读 |
| `card_read` | `{ card_id }` | `{ card_json, state_json }` | 只读 |
| `card_state_write` | `{ card_id, patch_json }` | `{ bytes }` | 写盘（64 KiB 在 Rust 侧再兜一层） |
| `card_delete` | `{ card_id }` | `{ dir }` | 写盘（挪 `.trash`） |
| `card_export_html` | `{ card_id, out_path }` | `{ bytes }` | 写盘（单文件导出，**B4 可选批**） |

Rust 侧校验全部 fail-loud：`card_id` 名字围栏（拒 `..` / `/` / `\` / `:`）、
`card.json` 可解析且 `kind` 在册、`payload` 可序列化、写盘先 `.tmp` 再 rename。

## 6. 流通（可独立后置）

**卡片导出为单文件 HTML**：把 `card.json` + `state.json` 灌进一个自带运行时的 HTML，
双击即可在任意浏览器打开，状态用 `localStorage` 打底。

这比 showcard 的 `.card.zip` 强一档：**不需要对方装任何软件**。
地基已有九成——`buildHtmlCardDocument()`（`plugins/builtin/renderers/components.tsx`）
本来就在做「往 HTML 里注沙箱 + CSP + 状态桥」，缺的只是「把注入改成自带运行时 + 快照」。

**明确不做**：`.card.zip` 交换格式、manifest 声明工具绑定、跨宿主能力协商——那些是 showcard 的使命。

## 8. 验收（六条，用户视角）

1. **卡片留得住**：把一张待办卡存进架阁 → 删掉那个会话 → 架阁里的卡还在，勾选状态也在。
2. **软件看得见**：装了笔记软件（`examples/plugins/notes-app`）→ 顶部浮件点 `架阁` → 软件页里有它 → 点开 = 开窗，不必叫 Agent。
3. **两页分明**：软件型 / 卡片型各自陈列，空态各有一句诚实的话和一个出口。
4. **不打扰纸面**：图版架行为逐字不变；浮层关闭后画布状态完全复原。
5. **收是用户的手势**：Agent 无法把卡片塞进架阁（工具面无新增 action）。
6. **能带走**（若做 B4）：导出的 HTML 在任意浏览器双击可用，零网络请求、零控制台异常。

## 9. 边界（本方案不做）

- **不做**卡片的工具调用 / 网络授权 / 能力协商（D4）；
- **不做**跨软件交换格式与外部标准兼容（D5）；
- **不做**卡片的后台运行、定时唤醒、进程（卡片永远是「数据 + 渲染器」）；
- **不改**软件四件套的任何字段与语义（窗口 / 地盘 / 受治进程 / 后台唤醒一律不动）；
- **不做**卡片的版本管理、同步、去重（同内容两张卡 = 两个实体）；
- **不做**旧数据迁移（D6）；
- **不做**首页入口（D9）；**不做**浮层拖动/缩放（D10）；
- **不做**「启动器」的完整产品面（任务栏 / 开机启动 / 最近使用）——本方案只给门与册，
  真需要时另立。

## 11. 已拍板与遗留

**已拍板（2026-12-08，用户）**：
1. 两件一起做（软件的门 + 卡片的家）。
2. 入口在标题栏（画布顶部浮件），点开专用浮层窗，分「软件型」/「卡片型」两页。
3. **入口名 = 架阁**（与 `画布` 同族的双字件）。两页仍叫「软件型」/「卡片型」。
   词源自洽：兰台是汉代皇家藏书/档案处，**架阁库**是宋代收藏文书的库房——同一个体系里的词。

**术语分工（避免混淆）**：
- **架阁** = 产品面（用户点开看见的那本浮层，两页）；
- **图版架** = 本卷收纳条（`.pp-composer` 下缘那条 880×38，不动）；
- **卡片库** = 底层存储（`~/.lantai/cards/` + `card-library.ts`，用户不需要知道这个名字）。

**遗留待定（不阻塞 B1/B2，可在 B3 开工前定）**：
- 首页顶栏是否也放架阁（D9 默认本批不放）。
- 卡片页的排序：存进时间倒序（我建议这个）还是按类型分组。

## 附：与 showcard 的关系（一句话）

showcard 定义「**卡片是什么**」（跨软件的可携带格式）；本方案定义「**物在兰台怎么活**」（身份/地盘/门）。
前者是标准，后者是产品；不冲突，也不同层。本方案只借了它两条纪律：
**拓印而非链接**（D3）、**收藏不等于信任**（D4 的反面：我们干脆不给卡片权力）。
