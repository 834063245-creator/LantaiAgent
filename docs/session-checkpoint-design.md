## 0. 动机：三次事故，一个根因

兰台会话层历史上三次翻车——**铺卷化石**、**双轨写盘**、**归零重建**——表面症状各不相同，
根因是同一句话：**「会话什么时候算已持久化」从来没有被定义过**。

现状的落盘时机散落在「偶然路径」上：UI 事件、流结束回调、防抖计时器、失活钩子……
每次重构都在重新洗牌这些偶然时机，而没有任何一处代码能回答：

- 模型正在生成时崩溃，用户丢多少？（答案取决于防抖窗口里有什么）
- 工具刚写完文件后崩溃，模型知不知道自己写过？（答案：不知道——卷里没有这段）
- 重启后恢复的会话，到底是哪个时刻的状态？（答案：最后一次 autoSave 成功的时刻，而这个时刻的选择没有语义，只有频率）

DSH（DeepSeek Harness）对同一问题的解法是 **checkpoint-policy**：在「模型请求前」和
「工具副作用前」两个语义时刻落持久化检查点，其余时刻一概不承诺。本设计采用同样的
两个触发点，落点与实现按兰台现状定制。

## 1. 现状盘点（2026-09-02 实测）

设计之前先把「现在到底有什么」钉清楚。兰台会话持久化是**三层面**：

### 1.1 会话卷（用户恢复的主面）

- **写链**：`ui/chat-session.ts` `writeSessionSnapshot` → `typedRpc('write_file_content')`
  → `src-tauri/src/confined_fs.rs` `write_text` → `crate::utils::write_atomic`（**临时文件 →
  rename，原子替换**）→ `{projectPath}/.lantai/sessions/{id}.json`。
- **形状**：单卷单文件全量快照（`SessionSnapshotData`：id/label/savedAt/messages/
  uiMessages/tokensUsed/compose）。
- **当前触发时机**（这正是问题所在——全部是偶然时机，无语义定义）：
  - `scheduleAutoSave`：**500ms 防抖**合并密集触发（`AUTO_SAVE_DELAY_MS`），带
    H5 代际守卫（延迟触发时工作区已切换则丢弃）；失败 toast 可见（错误不静默）。
  - 调用源：消息变异（chat-session L450）、流结束（chat-stream L495）、持久化订阅
    壳行（shell/rows/persistence.ts L41/L87）、失活/设置重初始化的显式保存。
  - 改名即存（C8）、合卷自动存共用同一写盘函数。

  **现状触发时机全图**（「偶然时机」的完整证据面——触发点 A/B 落地后，
  下表左列全部退役为「语义时刻的下游」或删除）：

  | 触发源 | 位置 | 时机语义 |
  |---|---|---|
  | 消息变异回调 | `ui/chat-session.ts` L450 | 每次 append/replace 后触发防抖 |
  | 流结束 | `ui/chat-stream.ts` L495 | 本轮流式收尾时触发防抖 |
  | 持久化订阅壳行 | `shell/rows/persistence.ts` L41 | 会话事件信号 → 防抖 |
  | 持久化订阅壳行 | `shell/rows/persistence.ts` L87 | 工作区失焦/失活 → 防抖 |
  | 改名即存 | `saveSessionById`（C8） | 改名动作直写 |
  | 合卷自动存 | 合卷路径 | 换卷时直写 |
  | 显式保存 | 失活、设置重初始化 | 直写 |

- **边界**：空会话（仅系统提示）**不落盘**；坏卷读路径直接从摊开集过滤（见 §3.2）。

### 1.2 事件日志（会话事件溯源）

- **写链**：Agent 变异三入口（`_appendMessage` / `_replaceSession` / `_retractSessionRange`，
  spec AST 白名单 + gate 双层门禁）→ `SessionLog` → `agent/logger.ts` →
  `typedRpc('log_append')` → Rust `OpenOptions append + writeln`（逐行追加）。
- **纪律**（CONVENTIONS 1.7）：新增持久化路径必须沿用 `_eventAppendChain` 串行写链
  （防并发 saveState 重复追加）。

### 1.3 NDJSON 消息追加（Rust 侧唯一可单测的落盘实现）

- `src-tauri/src/rpc.rs` `agent_session_append`：`.lantai/agents/{agent_id}/session.ndjson`，
  append-only；`rewrite=true` 时 truncate 全量重建。**本次 Phase 2 已将其行为序列钉死**
  （round-trip / 空会话 / 损坏容忍 / 并发字节完整性 / 覆盖语义——见 §8）。
- 现状注记：其前端消费面（agent-store 持久化写面）已于 2026-09-01「积尘根治」拆除，
  命令仍在 RPC 契约内（dormant-but-contracted）。钉测它不是因为它是当前活跃主面，
  而是因为它是 Rust 侧唯一零状态、可单测的会话落盘实现——其语义（追加/截断/OS 追加
  原子性）正是本设计恢复保证的物理基础。

### 1.4 seam（平台化 D11，2026-08-27）

- `composition/session-persistence-service.ts`：`ctx.sessionPersistence` 通道 +
  `SessionPersistenceProvider` 注册表（后注册胜）+ 默认 provider
  `builtin/rust-sessions`（agent/sessions-provider.ts，动作→命令恒等映射，
  五个动作：read/write/append/appendLog/mkdir/delete）+ `seam/sessionPersistence`
  组合裁剪域。
- 消费面现状：agent-store 退役后**无活跃消费者**；卷写链保持 typedRpc 直连
  （施工⑥范围注记：冻结文件，P5 统一挂 seam）。详见 §4 核验。

### 1.5 现状结论

三层面各自有写原子性与守卫，但「**何时**落盘」由防抖频率而非语义时刻决定。
500ms 防抖在**稳态**下足够密（最长丢 500ms 内容），但在以下两个窗口暴露本质缺陷：

1. **模型请求窗口**：请求发出 → 重试退避（Phase 1 后 transient 最多 3 次尝试 × 1s→4s
   退避，窗口可到 10s+）→ 流式生成（数十秒）。崩溃丢整轮。
2. **工具副作用窗口**：副作用不可回滚，但卷里没有「模型即将执行 X」的痕迹。
   崩溃后重启，模型对世界状态的判断与磁盘事实脱节。

这两个窗口就是两个触发点的由来。

## 2. 设计总纲

**一句话**：把「何时持久化」从偶然频率（500ms 防抖碰上了什么）收编为两个语义时刻——
检查点之后、下一个触发点之前发生的任何崩溃，丢失面都有明确定义。

四条原则（与项目宪法对齐）：

1. **复用唯一写链**：检查点不是新的持久化实现，只是在既定时刻调用既有写链。
   自建第二写面 = 「双轨写盘」事故的复刻，本设计的第一红线。
2. **错误不静默**：检查点失败必须可见（toast/console），且不阻断主流程（见 §3.3）。
3. **零新写模式**：落盘原语只有两个（原子全量替换、OS 追加），检查点不引入第三种。
4. **只做语义，不做迁移**：本设计定义时刻与保证；接线（在哪一行代码调用）是
   实施工程项，不在此范围内。

## 3. 两个触发点

### 3.1 触发点 A —— 模型请求前（pre-request checkpoint）

**定义**：Agent 主循环内，本轮请求载荷（messages + tools）组装完成之后、
`provider.stream()` 发出之前的时刻，对当前会话落一次检查点。

**挂钩位置（实施参考，本设计不接线）**：平台化 P5 后流式循环 = `ctx.agentLoop`
的第一方默认实现（`agent/agent-loop/`，非冻结文件）——触发点 A 挂在其主循环
「组装请求 → 发起请求」之间；检查点动作复用 §1.1 卷写链。

**为什么是这里**：

- 请求是本轮中最长的不可中断窗口（重试退避 1s→2s→4s × 3 次尝试 + 流式生成，
  可到数十秒）。检查点之后，磁盘卷已包含「全部已完成轮次 + 本轮全部输入」；
  此后任何时刻崩溃，重启恢复的会话不丢用户已说的话。
- 该时刻会话在逻辑上是**静默点**：没有在途流式内容、没有半截工具结果——
  快照序列化无竞态，是全卷原子替换的天然安全点。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 每轮一次全量写 = 写放大（大卷 MB 级时明显） | 复用 500ms 防抖链合并；脏标记（同轮已检查点且会话未变异则跳过）；大卷降频为可配策略（§9 开放问题 1，实施时定参） |
| 检查点在请求路径上增加延迟 | 写盘在 spawn_blocking（既有），主循环不等 fsync；检查点失败不阻断请求（§3.3） |

### 3.2 触发点 B —— 工具副作用前（pre-side-effect checkpoint）

**定义**：写类工具（fs write/edit、shell、browser/desktop 写动作——凡产生
world-diff 的动作）`execute` 之前的时刻，对当前会话落一次检查点。

**挂钩位置（实施参考，本设计不接线）**：工具管道裁决链 = `agent/events.ts`
AgentEventBus 的 guard/preflight/around 组合（P5 后生产路径已是 eventBus）——
触发点 B 挂在写类工具的 preflight/around 节点，读类工具不经过。

**为什么是这里**：

- 工具副作用**不可回滚**：文件已写、命令已跑。副作用后崩溃，卷里却停留在
  「模型即将执行 X」之前——重启后模型对「我做过什么」的判断与磁盘/代码库
  事实脱节，直接后果是重复执行写动作或无视已产生的残留（三次事故里
  「铺卷化石」的行为形态）。
- 副作用前检查点 = 磁盘卷记录了「模型宣布了要执行什么」。配合事件日志
  （工具调用事件经三入口入 log），崩溃恢复后能精确重建「哪些副作用可能已发生」，
  把不可知窗口压缩到「单个工具执行中」。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 写工具高频轮次（批量编辑）触发过密 | 只对写动作检查点（读工具零成本）；脏标记合并（会话未变异不重复写）；防抖链天然合并突发 |
| 与触发点 A 重复落盘 | 同轮内 A 已落且会话未变异 → B 跳过（脏标记） |

### 3.3 检查点失败的处理（与 DSH 的刻意差异）

检查点是**保证，不是门禁**：

- 失败 = toast/console 可见（错误不静默），但**不阻断**请求发出或工具执行。
- 理由：检查点错过的代价是「崩溃时丢这一轮」；做成门禁的代价是「磁盘满/
  权限错时用户完全不能用」——后者把可恢复的降级变成硬死锁。
- 下一个触发点自动重试（每轮/每次写工具都会再试）。

**方案取舍记录**（失败语义三选一，实施期不再重议除非有新证据）：

| 方案 | 行为 | 判决 |
|---|---|---|
| Ⅰ 阻断（DSH 形态） | 检查点失败 → 请求/工具不发 | ❌ 磁盘满 = 全功能瘫痪，把降级变死锁；DSH 无桌面单机盘满常态，兰台有 |
| Ⅱ fail-open + 可见（**采纳**） | 失败可见、流程继续、下个触发点重试 | ✅ 丢失面上界明确（≤1 轮），可用性优先 |
| Ⅲ 失败计数升级 | 连续 N 次失败后转阻断 | ⏸ 记为开放问题 §9.4（默认永不升级；有真实磁盘故障样本再议） |

### 3.4 一轮对话的检查点时序（设计推演）

```
用户输入 ──► 卷检查点 A①（请求前：含本轮输入的完整状态已上盘）
              │
              ▼
        模型请求 ──流式生成──► 流结束 ──► autoSave（既有防抖，不变）
              │
              ▼
        模型宣布工具调用 X(写)
              │
              ├─► 卷检查点 B（副作用前：卷里已有「即将执行 X」的痕迹）
              │
              ▼
        工具 X 执行（不可回滚副作用）
              │
              ▼
        工具结果回填会话 ──► 卷检查点 A②（下一轮请求前，含 X 的结果）
              │
              ▼
        …循环…
```

- A① 落盘内容 ⊇ 用户输入 → 崩溃不丢「用户说了什么」。
- B 落盘内容 ⊇ 「模型宣布执行 X」→ 崩溃后卷与事件日志可重建「X 可能已执行」。
- A② 落盘内容 ⊇ X 的结果 → 崩溃后模型已知 X 已完成，不会重执行。

### 3.5 崩溃恢复矩阵（各窗口丢失面推演）

| 崩溃时刻 | 卷上最后状态 | 恢复结果 | 丢失面 |
|---|---|---|---|
| A① 之后、请求中/重试退避中 | 含本轮输入的完整快照 | 重启续聊，本轮输入在卷 | 零（模型尚未产出） |
| 流式生成中 | 同上 | 同上；部分生成内容只存在于内存 | ≤1 轮模型输出（用户重新触发） |
| B 之后、工具执行中 | 含「宣布执行 X」的快照 | 重启后卷 + 事件日志可见 X 已宣布 | X 的副作用可能已发生——模型续聊时可见日志痕迹，避免重执行 |
| 工具结果回填后、A② 前 | B 的快照（不含 X 结果） | 卷缺 X 结果 | ≤1 个工具结果（事件日志佐证） |
| 任意时刻（现状对照） | 500ms 防抖窗口内的偶然状态 | 不确定——取决于崩溃撞上哪个窗口 | 无定义 ← 本设计消灭的正是这一行 |

## 4. 恢复保证

### 4.1 写盘原子性

| 写面 | 原语 | 保证 | 依据 |
|---|---|---|---|
| 卷快照（全量） | `utils::write_atomic`：临时文件 → rename | 读者只见旧卷或新卷，永不见半写卷；NTFS 同卷 rename 原子 | confined_fs::write_text 现状，chat-session 注释同款 |
| 事件日志 / NDJSON（增量） | `OpenOptions append` + 单次 `write_all` + `flush` | 单次 WriteFile 在 FILE_APPEND_DATA 下原子续尾——字节零丢失 | Phase 2 钉测 ④（并发 80 次追加零丢字节） |

检查点**零新写模式**：全量走 write_atomic，增量走 append。不存在第三种落盘方式。

### 4.2 损坏回退（读端容毒，写端不美化）

- **卷 JSON 损坏**：读路径（`listSavedSessions` / `readVolumeData`）墓碑与坏卷
  过滤——坏卷不进摊开集、不产生「每次启动必崩」（INVARIANTS #11 家族）。
  原文件保留在盘，可人工修复；不静默吞（打开失败必须可见报错）。
- **NDJSON / 事件日志坏行**：读端逐行解析、跳过坏行容毒。
- **追加面对损坏文件的现状语义**（Phase 2 钉测 ③，不美化）：
  追加不解析、不清洗既有内容——损坏带尾换行 = 垃圾保留 + 新合法行续尾；
  损坏不带尾换行 = 新记录与垃圾尾**熔接成非法行**（现状不补换行）；
  **真正的恢复路径 = `rewrite=true` 截断重写**（前端全量重建），损坏历史被清除。
- 检查点不改变上述任何语义——它只是「更多时刻的卷快照」，坏卷过滤与
  rewrite 重建路径原样适用。

### 4.3 锁策略

1. **单写者原则**：会话卷的写面在结构上只有一条（chat-session 写链，防抖
   timer 合并）。检查点**复用**该链而非并列新建——这是对「双轨写盘」事故
   的结构性回答：不存在两个写面，就没有两轨。
2. **进程内串行写链**：任何持久化路径必须沿用 `_eventAppendChain` 式串行
   （CONVENTIONS 1.7 既有铁律），防并发 saveState 交错追加。
3. **epoch 守卫**：在途回调写盘前必须 `isCurrentEpoch`（INVARIANTS #12 / H5
   家族）——autoSave 已在位，检查点继承。
4. **跨进程**：会话卷无跨进程写者（引擎不写会话；多实例天然按工作区目录
   隔离）。同一 NDJSON 目标的并发追加依赖 OS 追加原子性（单次 write 完整、
   行级原子性不保证——Phase 2 钉测 ④ 已如实钉住，纪律 = 「一事件一 write_all」
   + 读端按行容错）。

### 4.4 恢复链端到端（重启 → 续聊的现状全链）

检查点改善的是链中「卷内容的新鲜度」，链本身现状已完备，本设计不改一环：

1. 启动 → `autoRestoreLastSession`（Q-B 拍板：不自动摊开，落案卷首页）→
   `scanMaxSessionId` 仅扫目录名对账发号（不读文件内容）。
2. 用户自选开卷 → `readVolumeData` → `readVolumeJSON` 读全量快照 →
   墓碑/坏卷过滤（`data.deleted` 或无有效 messages → 不进摊开集）。
3. Agent 构造（Agent 恒可构造——workspace-ownership 根治后的不变量）→
   会话上下文从卷快照恢复。
4. 事件日志按需补充（工具折叠/审计面），读端逐行容毒。
5. 摊开集语义 = 磁盘扫描推导（RESTORE_OPEN_MAX 最近 3 卷）——总目/tracker
   已退役，无第二真源。

**恢复保证的完整陈述**：检查点 A/B 保证了「卷内容在语义时刻是新的」；
`write_atomic` 保证了「卷要么是旧的完整、要么是新的完整」；坏卷过滤保证了
「坏卷不进恢复链但保留在盘」；epoch 守卫保证了「跨工作区在途写不串门」。
四者合起来，§3.5 矩阵里每一行的丢失面都有结构性支撑，不依赖运气。

## 5. 最小挂钩点与 D11 seam 满足度核验

### 5.1 挂钩点清单（实施时的全部改动面，本设计不实施）

| 触发点 | 挂钩位置 | 动作 |
|---|---|---|
| A 模型请求前 | `agent/agent-loop/` 第一方默认实现主循环（非冻结） | 调既有卷写链（saveActiveSession 或其等价） |
| B 工具副作用前 | `agent/events.ts` AgentEventBus 的写类工具 preflight/around 节点 | 同上 |

两处都是**在既定时刻调用既有函数**，不新增服务、不新增抽象层、不改 RPC 契约。

### 5.2 seam 满足度核验（结论：满足，零新契约）

D11 seam（`ctx.sessionPersistence`）逐项核对检查点需求：

| 检查点需要 | seam 提供 | 结论 |
|---|---|---|
| 全量落盘（write） | `SessionPersistenceProvider.execute('write', …)` → write_file_content（原子） | ✅ 覆盖 |
| 事件增量（appendLog） | `execute('appendLog', …)` → log_append | ✅ 覆盖 |
| 目录建立（mkdir） | `execute('mkdir', …)` → create_directory | ✅ 覆盖 |
| 读回/校验（read） | `execute('read', …)` → read_file_content | ✅ 覆盖 |
| NDJSON 追加（append） | `execute('append', …)` → agent_session_append（本次已钉测） | ✅ 覆盖 |
| provider 可替换/可观测 | 后注册胜 + `seam/sessionPersistence` 组合裁剪域 | ✅ 覆盖 |

如实记录的两个缺口（非本设计缺陷，属实施期决策）：

1. **消费面归一未决**：seam 当前无活跃消费者（agent-store 写面 2026-09-01 退役），
   卷写链仍是 typedRpc 直连（施工⑥范围注记：冻结文件，P5 统一挂 seam）。
   触发点接线前必须先决「检查点调用走 seam 还是直连」——否则正是双轨。
2. **execute 返回 string**：seam 动作返回命令直通字符串，无结构化「检查点结果」
   （如落盘字节数/fsync 确认）。当前需求用不到；若未来需要，扩 seam 动作是
   平台边界内的常规加面，不属本设计。

### 5.3 本设计的交付边界

本 Phase 的实际交付 = 本文档 + Phase 2 的五条行为钉测（§8）。**代码零接线、
时序零改动**——`cdp/session.rs` 与 `rpc.rs` 非测试代码未被本 Phase 触碰
（rpc.rs 仅按方向 A 做了行为逐字节不变的函数提取以支撑钉测，见 §8 注）。

## 6. 明确不做什么

1. **不做多后端 / 可替换存储抽象层**。D11 seam 已是唯一抽象层（provider 注册 +
   组合裁剪）；在它之上再造「checkpoint 后端」「存储策略层」= 给历史事故
   「双轨写盘」招魂。检查点是**时机**，不是**实体**——没有自己的类和状态。
2. **不做投影持久化**。卷快照（恢复主面）+ 事件日志（溯源面）双面已定；
   不为 UI 态（面板开合/选中/滚动位置）建第三持久化面——历史事故的
   「铺卷化石」形态之一就是把投影当状态存。
3. **不做迁移工具**。旧数据不迁移、直接归档是认可的标准操作（AGENTS.md
   破坏性授权第 4 条）；触发点上线后首次保存自然写新快照，无格式变化
   （快照形状不变），也就无从谈起迁移。
4. **不做时序迁移 / 行为变更**。本设计零代码接线；autoSave 现有触发面原样
   保留运行。触发点实施是独立工程项，须带本设计 + 门禁另行开工。
5. **不引入 OpenTelemetry 类观测基建**。检查点失败走既有可见面
   （toast/console），不搭监控栈。
6. **不做卷版本化 / .bak 多副本**。见 §9 开放问题 3——先记录，不预做。

## 7. 与 DSH checkpoint-policy 的对照

| 维度 | DSH | 兰台（本设计） |
|---|---|---|
| 触发点语义 | 模型请求前 + 工具副作用前 | 相同（这是本设计唯二拿来主义的点） |
| 会话存储形状 | 单一 per-session 文件 | 三层面：卷快照 + 事件日志 + NDJSON 追加（现状盘点 §1） |
| 检查点落点 | 会话文件本体 | 卷快照（恢复主面），事件日志自然跟随 |
| 失败处理 | checkpoint 失败阻断请求 | **fail-open + 可见**：不阻断（§3.3 的权衡，DSH 反向） |
| 双轨防御 | — | 复用唯一写链是第一红线（双轨写盘是本土事故史，DSH 没有） |

## 9. 开放问题（记录，不预做）

1. **大卷写放大**：MB 级卷 × 每轮触发点 A 的全量写。候选缓解：脏标记（默认开）、
   大卷降频（超阈值时仅 B 触发或每 N 轮一次）、增量 checkpoint——实施期用
   实测数据定参，本设计不定。
2. **消费面归一**：检查点调用走 D11 seam 还是 typedRpc 直连（§5.2 缺口 1）。
   对应施工⑥/P5 的既有计划，届时统一裁决；在那之前不接任何触发点。
3. **卷损坏的隔离备份**：凭证文件有「毒化隔离 + 备份重建」先例（INVARIANTS
   #11.2），会话卷目前只有坏卷过滤。是否给卷加 .bak 挪位——等第一次真实
   损坏事故或用户反馈再决（不预做）。
4. **检查点连续失败的升级路径**：fail-open 的极限是磁盘永久故障——连续
   N 次失败后是否升级为阻断请求（磁盘满时继续写工具是浪费钱）。默认
   永不阻断；实施期可加计数告警，不改默认语义。

## 10. 结论

本设计回答的问题只有一句：**「会话什么时候算已持久化」= 模型请求前 + 工具
副作用前两个时刻，外加既有的防抖 autoSave 与显式保存。** 每个时刻的丢失面
在 §3.5 矩阵中有明确定义，每个保证（原子写 / 容毒读 / 单写者 / epoch 守卫）
都有现状代码与 Phase 2 钉测背书。

交付边界再述：本文档是**语义与保证的定稿**，不是实施授权。触发点接线
（§5.1 两处挂钩）是独立工程项，开工前置 = 开放问题 §9.2 的消费面归一裁决；
届时本设计即实施规格，无需再写方案文档。
